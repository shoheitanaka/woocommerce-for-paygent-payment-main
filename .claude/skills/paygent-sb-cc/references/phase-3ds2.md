依頼項目1〜3に対応。SKILL.md の Phase 0 完了が前提。

## 1. 3DS2パターン制御値（VISA・カード名義人で制御）

出典: `2025docs/creditcard/モジュール・リンク共通/導入補足資料（EMV 3Dセキュア（ブラウザベース））.pdf` 5.1/5.2。
**金額での制御は使わない**（試験商品の価格をそのまま使う）。名義人と金額の両方が
制御値に該当した場合は名義人が優先される仕様。

### リスクベース認証（フリクションレス）— 名義人のみで完結

| RB-成功 | `BAVYA` | 決済成功 | - | - |
| RB-成功(attempt=0) | `BAVAA` | `no_tds_card`設定に依存※2 | 0 | - |
| RB-成功(attempt=1) | `BAVUA` | attempt設定に依存※1 | 1 | - |

### 異常系（全種類実施）

| パターン | 設定値 | 期待結果 |
| --- | --- | --- |
| ERR-RB-ActiveServerエラー | 名義人 `BBErrABAB` | 処理結果0/attempt=1（attempt設定に依存※1） |
| ERR-RB-取引タイムアウト | 名義人 `BCErrTimeOut` | 同上 |
| ERR-RB-報告電文チェックエラー | 名義人 `BDErrInvalidInput` | 同上 |
| ERR-CH-ActiveServerエラー | `BAVCA`＋パスワード `51001` | 同上 |
| ERR-CH-取引タイムアウト | `BAVCA`＋パスワード `30000` | 同上 |
| ERR-CH-報告電文チェックエラー | `BAVCA`＋パスワード `40000` | 同上 |

※1 attempt区分=1のパターンは、CC設定 `attempt`（アテンプト認定対応）が
yes なら決済続行＋`attempt_notice_email` へ通知メール、no なら決済不可が期待値。
**実施前に設定値を記録し、期待値をそれに合わせて解釈する。**
全パターンの挙動（通知メール含む）を検証するため、可能なら `attempt=yes` で実施を推奨。
変更した場合は終了時に戻す。

※2 RB-成功(attempt=0)（`BAVAA`）は `paygent_no_tds_card_response()`
（`class-wc-gateway-paygent-cc.php`）が処理する。CC設定 `no_tds_card`
（3D セキュア登録のないカードを受け入れる）が **no（デフォルト）の場合は
意図的にキャンセルされる**のが正しい挙動、**yes の場合は決済成功**が期待値。
Phase 0 で `no_tds_card` の値を記録し、期待結果をそれに合わせて解釈すること。
デフォルト（no）のままキャンセルされた場合はバグではなく仕様通りなので、
「決済成功」を無条件の期待値として扱わないこと。

## 2. 実行マトリクス（承認済み方針: 成功系フル・失敗系片側）

- **成功系5パターン**（RB-成功/RB-成功(attempt=0)/RB-成功(attempt=1)/CH-成功/CH-成功(attempt=1)）:
  {Block, クラシック} × {`paymentaction`=sale(売上), authorization(授権)} の **全4組合せ** = 20回
- **失敗・異常系9パターン**: {Block, クラシック} 各1回ずつ（設定は sale のまま）= 18回

進め方: `paymentaction=sale` で Block→クラシックの成功系＋失敗系を消化 →
設定を `authorization` に変更して成功系のみ再実施、が設定変更回数最少。

### 各決済実行時の確認項目（毎回記録）

1. チェックアウトで名義人パターンを入力して注文（商品は試験環境の既存商品）
2. チャレンジ系は認証画面でパスワード入力→送信
3. 成功系: サンクスページ表示 → 注文ステータス（sale=処理中/authorization=処理中または保留、
   実際の挙動を記録）→ 注文詳細の注文メモにPaygent応答（payment_id）が記録されていること
4. 失敗系: サンクスページへ進まないこと・**Paygentの実エラーが顧客に表示される**こと
   （Blockで「Something went wrong」だけならNG→既知バグ領域）・注文が失敗/保留のまま残ること
5. 支払い方法が「クレジットカード決済」のままであること
6. WP Mail Logging: 成功→新規注文(管理者)/注文処理中等(顧客)が**各1通**、
   失敗→注文完了系メールが送信されて**いない**こと、attempt=1続行時→アテンプト通知

### 授権(authorization)注文の売上化

授権設定で作成した成功注文のうち2件以上で、管理画面から売上処理
（注文ステータス変更または注文アクション。telegram 022）を実行し、
注文メモで成功を確認する。残りの授権注文はキャンセル試験用に残す。

## 3. 返金・キャンセル（依頼項目2）

上記マトリクスで作成した注文を使う:

| 操作 | 対象注文 | 手順 | 期待 |
| --- | --- | --- | --- |
| 部分返金 | 売上済み注文 | 注文詳細→返金→一部金額→Paygent経由で返金 | 成功・注文メモに記録（029補正売上） |
| 全額返金 | 売上済み注文（別件） | 同上・全額 | 成功・ステータス=返金済み（023売上取消） |
| オーソリキャンセル | 授権のみの注文 | 注文ステータス→キャンセル | 成功（021） |
| 売上後キャンセル | 売上化した注文 | 同上 | 挙動を記録 |

各操作後: 注文メモのPaygent応答、ステータス、WP Mail Loggingで
返金メール/キャンセルメールが**各1通のみ**（2重送信なし）を確認。

## 4. 通知確認（依頼項目3）

- WooCommerce→設定→メールの有効化状態を前提に、上記1〜3の各イベントについて
  WP Mail Loggingで「送信された/されていない/重複」を判定して一覧化する。
- 確認対象: 新規注文（管理者宛）／注文処理中・完了・返金・キャンセル（顧客宛）／
  アテンプト通知（`attempt_notice_email` 宛）。
- メール本文も1通は開き、金額・注文番号・文面崩れがないか確認する。
